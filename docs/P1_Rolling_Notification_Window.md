# P1：持续日期补排与通知容量

日期：2026-10-27。核心源码 `e336f05` 及边界修复 `9ec94b9` 已合入本地 main，统一使用 schema 16。P1.1–P1.3 为持续日期和共用容量实现，P1.4 为本次天气及记录边界收尾；系统送达与公开发布单独验收。

## P1.1 独立日期与持久化补排

- 出门计划保存一个管理记录，以及未来 60 个日历日范围内的独立日期事项。前一天未勾选不会阻止后一天；日期 ID 由计划和实际出门日期组成，跨午夜提前提醒仍属于对应的出门日。
- 启动、前台恢复和前台维护会补齐缺失的未来日期；前台维护最多每分钟尝试一次，没有出门计划时直接返回。长时间未打开应用，只补当前未来窗口，不制造期间未曾生成的历史事项。
- 重启与重复补排保留已完成、跳过、延后、未确认和单独删除的日期。旧单条出门周期记录转为管理记录时，保留原有当前日期；暂停、回收站中的计划不生成新的活动日期。恢复整组计划不会复活此前单独删除的日期。
- 常备清单按日期独立反馈；一次性项同步到计划和未来日期。独立日期仍提供“跳过本次”；用药剂次跳过记为“未服用”，不影响下一剂。
- 此窗口限制每次生成的未来范围，历史业务记录仍保留。关闭进程不会持续运行 Dart 补排；普通通用周期事项仍沿用原有推进方式，尚未全部改为独立日期。

验证：新增的跨重启、长时间缺席、删除／整组恢复、独立跳过与日历测试通过；洛杉矶时区专项 **43 项通过**，包含本页日期及容量专项，重复全量中的用例。

## P1.2 全局通知容量

| 平台 | 应用采用的预排预算 | 范围 |
| --- | --- | --- |
| iOS、macOS | 50 条 | 两个平台采用同一保守应用预算，不将 50 描述为系统硬上限 |
| Android | 400 条 | 为厂商差异留余量；后台限制、权限及精确闹钟仍需设备验证 |
| Windows、Linux | 不套用上述原生窗口 | 当前仍依赖应用内定时及既有平台实现；退出进程后的能力另验 |

- 普通事项、学习、出门和用药共用一个窗口，按未来触发时间、相同时间下的稳定 ID 选取。超出窗口的日期保存在业务数据库，显示为待补排，不丢弃、不误报为通知失败。
- 替换先取消旧请求再提交新请求；取消失败保留其容量，严格接口和兼容的尽力取消接口都不提前释放名额。故障回归先复现了预算 3 条却产生 4 条请求，修复后最大值保持 3。
- 不确定的提交先保留名额，下次先取消再重试。冷启动从本机通知日志恢复可能存在的请求，维护重建、专注策略切换及前台到期释放均使用相同窗口。
- 前台到期后补入后续日期；后台系统送达不会自动执行应用内补排。恢复应用后再按当前业务状态补排。已到期的保留横幅不会因释放名额而统一删除。
- 使用现有数据代次、维护门禁和本机通知日志，不新增业务表或提升 schema。通知日志不作为业务备份导入。

预算依据为已锁定的 [flutter_local_notifications 17.2.4 平台限制说明](https://pub.dev/packages/flutter_local_notifications/versions/17.2.4#-caveats-and-limitations)。该说明区分 iOS 请求限制与部分 Android 厂商限制；没有将 macOS 或所有 Android 设备视为相同硬上限。真实队列应通过系统独立读回核对，例如 Apple 的 [getPendingNotificationRequests](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/getpendingnotificationrequests(completionhandler:))。

验证：并发逆序写入、较早事项替换、取消失败、结果不确定、维护重建、冷启动日志恢复、专注模式、前台释放及不同计划共享预算均通过自动化替身测试；这些结果不等于真实系统容量与送达验收。

## P1.3 覆盖状态与回归集成

- 计划面板和通知修复页显示连续预排至何时、待补排数量和共用预算；缺少覆盖或没有未来提醒时使用独立文案，不显示无意义的日期占位。
- 连续覆盖按整个触发时刻检查；同一时刻有缺失、失败或因容量未选中的请求，就不会声称该时刻已完整覆盖。统计依据为当前业务状态和匹配轮次的本机日志，已提交不等于已送达。
- 单条事项详情区分待补排、需修复和策略暂停；待取消的旧请求仍提示需处理。计划状态可手动刷新、回到前台刷新、从修复页返回后刷新，支持仅日志变化后的重新读取。
- 合并已有的主动开启天气功能：出门前六小时内在前台预取，每计划 30 分钟冷却，每轮最多三个请求；网络等待不占数据库变更队列。返程观察时段可设为 1–1440 分钟。只有缓存到提醒触发时仍有效且时段完整时才给出雨情判断，否则保留基础清单并显示“天气待确认”；不承诺关闭应用后的天气刷新。

## P1.4 天气与记录边界收尾

源码 `9ec94b9`，在 `df4114e` 的 P1 验收基线上完成；没有增加业务表或改变 schema 16。

- 延后出门提醒时，以新通知触发时间重新校验缓存有效期，原定出门时间保持。缓存到新触发时间已经过期，就恢复基础清单、带伞待确认项与“天气待确认”，避免延用此前确定的雨情文案。
- 出门记录操作只修改观察记录，不能把编辑器里尚未启动的时刻、地点、城市、天气开关或学习授权写成正式配置。新观察使用已保存地点和天气快照；学习尚未正式开启时拒绝记录。清空／删除只接受现有记录的子集，带天气上下文的记录经 JSON 往返后仍可正常保留或删除。
- 解析阶段校验降雨阈值、记录保留天数、返回时段及重复星期，拒绝非法类型和范围。天气通知标注已缓存预报的来源、城市与获取时间；三语授权文案明确说明保存后会在前台预取。
- 旧单条出门计划转换独立日期时，若日期 ID 已被其他记录占用，整次事务拒绝，保留旧管理记录和提醒。单个出门日期也不能经普通编辑绕过计划预览而变为无限周期。
- 出门计划链接只加载匹配的计划类型，错误类型链接保留空白编辑器；详情入口采用出门图标。
